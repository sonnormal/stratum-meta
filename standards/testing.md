# 🧪 Stratum Comprehensive Testing Strategy

> **Architecture Reference:** Test Pyramid, Execution Topology, and Lifecycle Governance  
> **Testing Model:** Tier 1 (Unit in-memory), Tier 2 (Integration via Testcontainers), Tier 3 (Automated Multi-Service E2E via Docker/OrbStack). Tiers are executed 100% autonomously by AI agents; Human governance is exercised at 3 review gates.  
> **Applies to:** All Stratum Repositories (`services/*`, `gateway`, `web`, `meta`)

---

## 🏛️ Executive Overview

In **Stratum**, 100% of software code and infrastructure is generated by AI agents governed by Human-in-the-Loop review. Because code is authored autonomously, **testing is not an afterthought—it is the executable specification of the entire system.**

Stratum strictly follows **Test-Driven Development (TDD)** and organizes automated agent verification into three distinct architectural tiers:

```
                            ▲
                           / \
                          /   \
                         /     \     Tier 3: Automated E2E Testing (Cross-Service Journeys)
                        /  E2E  \    Target: Integrated Docker / OrbStack | Stored in: stratum-meta/tests/e2e
                       /---------\
                      /           \   Tier 2: Component & Seam Testing (Real DB / Redis Containers)
                     / Integration \  Target: Isolated Repo Sandbox (Testcontainers) | Stored in: <repo>/tests
                    /---------------\
                   /                 \  Tier 1: Pure Logic in Memory (100% Mocked)
                  /    Unit Tests     \ Target: Local Workspace / CI (Sub-second) | Stored in: <repo>/tests
                 /---------------------\
```

> [!IMPORTANT]
> **Strict Semantic Boundary: Tiers vs. Gates**
> * **Tiers (1, 2, 3)** are **automated execution boundaries for AI Agents**. Tier 3 is Automated E2E Testing executed by the AI test runner.
> * **Gates (1, 2, 3)** are **strategic review checkpoints for Human Stakeholders**. User Acceptance Testing (UAT) is performed by human stakeholders at `GATE-03` on the live stack. Never conflate Tier 3 with UAT.

## 📚 Formal Testing Foundations & Taxonomy (ISO/IEC/IEEE 29119 & ISTQB)

To ensure universal technical precision across all human reviews and autonomous AI engineering prompts, Stratum pins its verification taxonomy to canonical, version-dated international standards:

### 1. Canonical Standards & Publication Lifecycles
* **ISO/IEC/IEEE 29119 (Software and Systems Engineering — Software Testing):**
  * *ISO/IEC/IEEE 29119-1:2022* (Concepts & Definitions — 2nd Edition, Published **January 2022**; original standard published September 2013).
  * *ISO/IEC/IEEE 29119-2:2021* (Test Processes — 2nd Edition, Published **November 2021**).
  * *ISO/IEC/IEEE 29119-3:2021* (Test Documentation & Test Cases — 2nd Edition, Published **October 2021**).
  * *ISO/IEC/IEEE 29119-4:2021* (Test Techniques — 2nd Edition, Published **October 2021**).
* **ISTQB Standard Glossary of Terms Used in Software Testing:**
  * Version **4.0** (Published **May 2023** by the International Software Testing Qualifications Board; aligned with ISTQB Certified Tester Foundation Level v4.0).
* **BDD (Behavior-Driven Development / Specification by Example):**
  * Formalized by Dan North (**2006**) and canonical industry reference *Specification by Example: How Successful Teams Deliver the Right Software* by Gojko Adzic (**June 2011**).

### 2. Standardized Testing Taxonomy

| Concept | Formal ISTQB / ISO 29119 Definition | Meaning in Stratum (Human & AI) | Concrete Examples |
| :--- | :--- | :--- | :--- |
| **Test Assertion** | The atomic check of a single observable state or value. | A single line verification (`assert a == b`). | Checking that `status_code == 200` or `amount == Decimal("75000.00")`. |
| **Test Case** | A set of preconditions, inputs, actions, expected results, and postconditions developed for a particular test condition (strictly agnostic to manual or automated execution). | A specific situation or input variation being evaluated. | • **Case 1:** Inbox is empty.<br>• **Case 2:** Inbox has 1 VIB email.<br>• **Case 3:** Inbox has multiple VIB emails.<br>• **Case 4:** Non-bank email noise.<br>• **Unhappy Case:** IMAP server unreachable. |
| **Test Scenario** | An end-to-end operational story or business journey spanning multiple steps and boundaries. | Complete user workflow from external trigger to final stakeholder outcome. | Human has bank email in inbox → triggers batch → movement saved in DB → real Viber alert received on phone. |
| **Test Fixture** | The complete contextual baseline and test data required to execute one or more test cases deterministically (encompassing input datasets, sample files, mock server stubs, and pre-seeded database states). | All test data artifacts, sample emails, database seed rows, or configuration files fed into the test. | • Test Data: Raw `.eml` sample files<br>• Test Data: DB seed rows / JSON payloads<br>• Stubs: Mock HTTP server responses |
| **Test Suite** | A collection of test cases or test scenarios grouped for a specific execution objective. | The package of tests run at a gate or lifecycle tier. | • Tier 1 Unit Suite<br>• Tier 2 Integration Suite<br>• Tier 3 E2E Acceptance Suite |
| **Smoke Test Suite** | A selective subset of critical happy-path test cases executed to rapidly verify that core features and interfaces function before deeper testing. | The minimal sanity check run pre-flight or used by humans at `GATE-03`. | • Hitting `/healthz` on all containers<br>• Running 1 canonical happy-path end-to-end user journey |
| **Regression Test Suite** | A comprehensive test suite executed after code changes to ensure that previously developed and verified capabilities remain defect-free across all tiers. | The full multi-tier regression safety net preventing regressions across all historical features and formats. | • Monotonic Tier 1 in-memory tests<br>• Tier 2 parameterized tests against all historical fixtures<br>• Tier 3 canonical flow verification |

### 3. Canonical Test Case Categories (The 5 Standard Types)

Every Test Scenario in Stratum is evaluated across five canonical test case types (aligned with ISO/IEC/IEEE 29119-4 and ISTQB v4.0). This guarantees that both nominal execution and catastrophic failures are specified *before* code is synthesized:

| Category | Formal Standard Concept | Stratum Verification Purpose | Behavioral Invariant | Concrete Example (`CR-26j001`) |
| :--- | :--- | :--- | :--- | :--- |
| **1. Happy Path** | Positive Testing / Nominal Case (ISO 29119-4 §5.2.1) | Verifies standard valid inputs and primary success conditions where the business flow operates as intended. | System processes input end-to-end, produces correct state transitions, persists data, and emits expected output without error. | `TC-02` (Single) & `TC-03` (Batch): 1 or more valid VIB debit emails are parsed, Ollama extracts fields, row saved in Postgres, Viber push sent. |
| **2. Boundary / Edge** | Boundary Value Analysis / Extremes (ISO 29119-4 §5.2.3) | Evaluates behavior at the extreme limits of input ranges, empty collections, and state transition boundaries. | Zero index out-of-bounds, zero division-by-zero, clean handling of empty sets without raising uncaught exceptions or mutating state. | `TC-01`: Mailbox `INBOX` is completely empty (`count == 0`). System logs info message, performs 0 DB writes, 0 Viber alerts, exits cleanly with code 0. |
| **3. Negative / Noise Filtering** | Negative Testing / Equivalence Partitioning (ISO 29119-4 §5.2.2) | Verifies that irrelevant, malformed, or unauthorized inputs outside the domain model are safely rejected or discarded. | Inbound noise is filtered at the perimeter in sub-millisecond time without wasting GPU inference compute or polluting domain tables. | `TC-04`: Promotional marketing emails arrive in mailbox. Fast heuristic pre-filter discards them in < 1ms; Ollama is never invoked; 0 DB writes. |
| **4. Unhappy / Fault Recovery** | Fault Injection / Error Handling (ISO 29119-4 §5.3.4) | Verifies system resiliency, timeout handling, and graceful degradation when external boundaries fail or disconnect. | Zero unhandled crashes; system logs structured error codes, preserves current state, and leaves resources clean for recovery. | `TC-05`: Gmail IMAP connection drops, or Ollama GPU hangs, or Viber API returns HTTP 500. Service logs structured error, preserves batch offset, does not crash. |
| **5. Idempotency / Concurrency** | Concurrency / Duplicate Protection (ISO 29119-1 §4.4) | Verifies that re-submitting the exact same event or concurrent re-delivery produces identical state without duplicate records or repeated side-effects. | Database enforces atomic unique constraints (`ON CONFLICT DO NOTHING`); downstream consumers emit `DUPLICATE_IGNORED`; 0 duplicate notifications. | `TC-06`: Batch poller re-reads emails already ingested. Database row count remains exactly 1; returns `DUPLICATE_IGNORED`; 0 repeated Viber push alerts sent to phone. |

## 🔬 Tier 1: Unit Testing (In-Memory Isolation)

### 1.1 Definition & Purpose
Unit tests verify the smallest testable units of code (functions, pure domain entities, state transitions, mathematical calculations, and parsing logic) in complete isolation.

### 1.2 Key Rules
* **Zero Network, Zero Disk:** Unit tests must never make real network calls, connect to databases, or access the host filesystem.
* **100% Deterministic:** Unit tests must produce identical results regardless of environment, timezone, or machine state.
* **Blistering Speed:** Thousands of unit tests must execute in seconds to enable rapid inner-loop AI development.

### 1.3 Examples in Stratum
* Verifying that an email address parser in `gateway` correctly parses RFC 5322 headers and flags invalid domains.
* Validating that a currency calculation utility in `services/cashflow` rounds fractions according to business accounting rules.
* Checking that state machine transitions in `services/cashflow` correctly transition from `PENDING_REVIEW` to `SETTLED`.

## 🔌 Tier 2: Integration Testing (Seams & Side-Effects)

### 2.1 Definition & Scope
Integration testing in Stratum verifies the seams, communications, and stateful side-effects between application code and real external subsystems (databases, caches, message brokers, and downstream service contracts). Rather than merely asserting HTTP response codes, integration tests validate that real data transitions and side-effects occur reliably.

```
                       ┌──────────────────────────────────────────────────┐
                       │          INTEGRATION TEST SCOPE                  │
                       │                                                  │
    [ HTTP / gRPC Call ]──► [ Service Logic ] ──► [ Real PostgreSQL DB ]  │  (Asserts DB rows, constraints, rollbacks)
                       │          │                                       │
                       │          ├────────────► [ Real Redis Cache ]     │  (Asserts cache hits, invalidation & TTL)
                       │          │                                       │
                       │          └────────────► [ Real Kafka / Queue ]   │  (Asserts event emission & consumer ack)
                       └──────────────────────────────────────────────────┘
```

### 2.2 What Integration Tests Assert (Beyond API Payload)
1. **Database Persistence & Constraints:**
   - Did the record actually write to a real PostgreSQL database?
   - Are unique keys, foreign keys, and check constraints enforced?
   - Do database migrations run cleanly?
   - Do transactional rollbacks successfully revert state when an unhandled error occurs?
2. **Event & Message Bus Seams:**
   - When an order is placed, was an `OrderCreatedEvent` published to the message broker?
   - Are messages serialized correctly according to protobuf/Avro/JSON schemas?
   - Does a consumer correctly acknowledge (`ack`) or dead-letter (`nack`) malformed messages?
3. **Cache & State Stores:**
   - Does a cache hit return cached data without querying the database?
   - Does a mutation invalidate the appropriate cache keys in Redis?
4. **Resilience & Fault Tolerance:**
   - How does the service behave when the database times out or returns a connection error? Does it retry gracefully or return a sanitized error message?

### 2.3 Independent Repository Isolation via Testcontainers
In Stratum's multi-repository architecture, each repository must be developed and tested **completely independently**:
* Microservice repositories (`services/cashflow`) must **never** depend on running sibling services (`services/auth`) during integration tests.
* Instead, integration tests use **Testcontainers** (ephemeral Docker containers managed programmatically):
  - When tests start, Testcontainers spins up a real, clean PostgreSQL or Redis container in OrbStack/Docker.
  - Sibling microservices and external third-party APIs (e.g. Zalo Bot API, Payment Gateways) are simulated using strict **HTTP WireMocks** or **OpenAPI Contract Mocks**.
* **Repository-Scoped Scenarios & Fixtures:** Because Tier 1 (Unit) and Tier 2 (Integration) tests run against a single isolated repository, both the test scenarios (`scenario.md` reviewed at `GATE-02`) and test fixtures (`fixtures/` containing sample emails, mock payloads, or seed data) are housed **directly in that specific repository** (e.g., `<repo>/changes/CR-YYaXXX-<short-title>/`). They do not live in the global `meta` archive.
* **Benefit:** 100% of integration tests pass in complete isolation on your local machine before staging is ever touched.

## 🌐 Tier 3: End-to-End (E2E) Testing (Cross-Service Journeys)

### 3.1 Definition & Core Invariants
* **Tier 3 (Automated E2E Testing):** Tier 3 is an automated execution tier executed 100% autonomously by AI agents. It verifies that interconnected microservices, network ingress, databases, host inference, and messaging gateways function correctly from the outside in.
* **UAT (Human User Acceptance Testing):** UAT is a human governance activity performed at `GATE-03`. It is not an automated tier.
* **Execution Environment:** By default, Tier 3 automated E2E tests execute locally against containerized multi-service topologies running in **Docker / OrbStack**. Cloud UAT environments serve as optional staging targets for distributed webhook accessibility.

---

### 3.2 Repository Scoping & Architecture
To preserve strict microservice decoupling:
* **Microservice Repositories (`services/cashflow`, `gateway`):** Contain **zero** multi-service E2E tests. Microservice repositories only contain Tier 1 (Unit) and Tier 2 (Integration via Testcontainers) suites.
* **Meta Repository (`stratum-meta`):** Acts as the single central home for all multi-service E2E test code, orchestration scripts, and ecosystem fixtures:
  * **`stratum-meta/tests/e2e/`**: Python/Playwright E2E test scripts exercising cross-service boundaries.
  * **`stratum-meta/scripts/`**: Orchestration and verification harnesses (e.g., `uat-verify.sh`).

---

### 3.3 How the Human-Reviewed UAT Suite Comprises the Automated E2E Suite

The human-reviewed acceptance suite directly drives and comprises the automated Tier 3 E2E suite through a 4-phase lifecycle:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. DEFINITION (GATE-02)                                                │
│ Human reviews & approves Acceptance Criteria & Scenarios (TC-01..06)   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ AI Agent synthesizes E2E code
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. AUTOMATION & PRE-FLIGHT (STEP-04 ➔ STEP-06)                         │
│ AI implements TC-01..06 in stratum-meta/tests/e2e/ & scripts/          │
│ AI executes automated E2E suite against live containers (OrbStack)     │
│ Scorecard generated: uat_results_YYYYMMDD_HHMMSS.md                    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Scorecard delivered to Human
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. VERIFICATION & SMOKE (GATE-03)                                      │
│ Human inspects automated scorecard (validating all edge/unhappy paths) │
│ Human picks critical paths (TC-02) to smoke-verify on physical phone   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Promotion upon sign-off
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. REGRESSION PROMOTION (STEP-07)                                      │
│ Canonical business journey promoted to stratum-meta/tests/e2e/regress/ │
│ Boundary variations & error permutations pushed down to Tier 2 fixtures│
└────────────────────────────────────────────────────────────────────────┘
```

1. **Specification Mapping at `GATE-02`:**
   * Human reviews the plain-language acceptance test suite in `scenario.md`.
   * Each acceptance case defines explicit preconditions, trigger events, cross-service interactions, and expected side-effects (e.g., `TC-01` Empty Inbox, `TC-02` Happy Path Single, `TC-03` Batch, `TC-04` Noise Filter, `TC-05` Unhappy/Outage, `TC-06` Idempotency).
   * **Invariant:** The human defines *what* behaviors must be accepted; the AI agent translates every single accepted case 1-to-1 into executable Tier 3 E2E test code.
2. **Autonomous E2E Implementation & Pre-Flight in `STEP-06`:**
   * The AI QA Agent authors the automated E2E harness in `stratum-meta/tests/e2e/` and `stratum-meta/scripts/uat-verify.sh`.
   * Before the human is notified for `GATE-03`, the test runner executes the entire automated suite against the live Docker stack.
   * The test runner generates a timestamped execution scorecard (`uat_results_YYYYMMDD_HHMMSS.md`) recording pass/fail, execution durations, database state diffs, and structured error logs.
3. **Human Smoke Selection at `GATE-03`:**
   * Because the automated E2E suite proved all technical invariants (e.g., that an empty inbox cleanly exits without DB mutations, that timeouts log structured errors without crashing, that re-runs are idempotent), **the human does not need to manually repeat all edge cases.**
   * The human reviews the automated scorecard, and selectively picks 1–2 canonical cases (such as triggering an email to see the physical Viber push notification on their physical phone) for smoke verification.
4. **Lean E2E Regression Promotion in `STEP-07`:**
   * Running hundreds of full multi-service E2E tests across dozens of CRs creates slow builds and network flakiness.
   * **CR Acceptance Suite:** Bound to the specific change request (`CR-26j001`). Exercises all permutations for that release candidate.
   * **Canonical E2E Regression Suite:** Upon promotion, only the primary happy-path business journey (e.g. `FLOW-001` Ingestion to Notification) is merged into the permanent cumulative E2E suite in `stratum-meta/tests/e2e/regression/`.
   * **Push-Down to Tier 2:** Negative cases, parsing quirks, and timeout scenarios from the UAT suite are pushed down to Tier 2 Integration tests backed by captured fixtures.

### 3.4 Integration Test Fixture Improvement & Feedback Loop

Integration test fixtures must not remain static synthetic stubs. They evolve into an enterprise-grade regression corpus through an automated harvesting and promotion cycle:

```
[ STEP-04: TDD Red ]
Synthetic Stubs (<repo>/changes/CR-*/fixtures/synthetic_*.eml)
         │
         ▼
[ STEP-06: Live Pre-flight & UAT ]
Ingestion Gateway captures raw real-world payloads
         │
         ▼
[ Temp Capture Log ]
scratch/harvested/raw_<source>_<timestamp>.raw
         │
         ▼
[ Automated Sanitization Protocol ]
1. PII & Token Redaction (Mask account numbers, tokens, emails)
2. Structural Invariant Preservation (100% verbatim MIME, HTML, CSS, encodings)
         │
         ▼
[ STEP-07: Promotion to Permanent Corpus ]
<repo>/tests/fixtures/real/<bank>_<template_version>_<descriptor>.eml
         │
         ▼
[ Monotonic Tier 2 Parameterized Binding ]
@pytest.mark.parametrize("fixture", glob("tests/fixtures/real/*.eml"))
Every future commit automatically verifies every historical real-world format
```

#### 1. Phase 1: Cold-Start via Synthetic Fixtures (`STEP-04`)
* During initial TDD authoring, real payloads may not yet exist in the repository.
* The AI agent authors synthetic fixtures based on interface contracts and vendor documentation, saved to `<target-repo>/changes/CR-YYaXXX/fixtures/`.
* *Limitation:* Handcrafted fixtures rarely capture subtle anomalies found in production (e.g. weird MIME transfer encodings, non-standard HTML table nestings, invisible non-breaking spaces `\u00a0`, or malformed header timestamps).

#### 2. Phase 2: Live Payload Harvesting (`STEP-06`)
* When live UAT executes against external boundaries (e.g., pulling live emails from stakeholder mailbox), the service writes raw incoming payloads byte-for-byte to a local capture buffer: `scratch/harvested/raw_<source>_<timestamp>.eml`.

#### 3. Phase 3: Sanitization Protocol
Before any harvested payload can be committed to a git repository, it must pass strict automated sanitization:
* **PII & Secrets Redaction:**
  * Replace bank account numbers with masked test equivalents (e.g., `***1234`).
  * Replace stakeholder names and recipient emails with standardized test personas (`test-user@stratum.local`).
  * Strip session tokens, API keys, and routing IP headers.
* **Structural Invariant Preservation:**
  * Preserve exact MIME multipart boundaries, `Content-Transfer-Encoding` (`base64`, `quoted-printable`), raw HTML hierarchy, inline styles, whitespace, and Unicode character encodings 100% verbatim.
  * Preserving byte-level structure ensures parser regression tests test real-world parser fragility, not synthetic ideals.

#### 4. Phase 4: Permanent Retention Invariant (`STEP-07`)
* **The Rule:** Every unique bank format, template variation, or notification layout ever observed in the wild is preserved **indefinitely** in `<repo>/tests/fixtures/real/`.
* Fixtures are never overwritten. If VIB Bank changes its email template layout from a 2026 format to a 2027 format:
  * The old fixture remains: `vib_transfer_v1_table.eml`.
  * The new format is added: `vib_transfer_v2_card.eml`.

#### 5. Phase 5: Parameterized Tier 2 Regression Binding
* The repository's Tier 2 integration test suite binds dynamically to the growing fixture corpus:
  ```python
  @pytest.mark.parametrize("fixture_file", glob.glob("tests/fixtures/real/*.eml"))
  def test_cashflow_parser_against_all_historical_fixtures(fixture_file):
      # Ensures new code never breaks parsing of any historical format
  ```
* This achieves **monotonic regression hardening**: the regression test suite becomes stronger with every release without human engineers having to manually write new test methods.

---

### 3.5 Execution Topology: Local Workstation Runner vs. Live Targets

* **Default Local Execution:** The automated Tier 3 E2E test runner executes on the local workstation against local Docker/OrbStack containers. All dependencies (PostgreSQL, Ollama host GPU, local containers) run locally at zero cloud compute cost.
* **Live Target Parity:** Ingestion boundaries connect to live external endpoints (e.g., real IMAP inbox, real Viber Bot API) using credentials securely injected from `.env.secrets`. Artificial simulation or cheat bypass endpoints inside production containers are strictly forbidden.

## 🎯 Summary Takeaways

1. **Unit Tests (Tier 1):** Fast, in-memory, zero-dependency. Catch logic flaws instantly. Authored in `STEP-04` (Red), satisfied in `STEP-05` (Green).
2. **Integration Tests (Tier 2):** Essential. Test real database constraints, transactions, and event streams via Testcontainers inside isolated repositories. Catch 85–90% of bugs before staging. Authored in `STEP-04` (Red), satisfied in `STEP-05` (Green).
3. **End-to-End Tests (Tier 3):** Automated cross-service journeys stored in `stratum-meta/tests/e2e/` and `scripts/`. Executed in `STEP-06` as an automated pre-flight gatekeeper before `GATE-03`. Follows the Lean Regression policy: canonical flows are promoted to Tier 3 regression, while format permutations and error edges push down to Tier 2.
