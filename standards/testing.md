# 🧪 Stratum Comprehensive Testing Strategy

> **Architecture Reference:** Test Pyramid, Execution Topology, and Lifecycle Governance  
> **Phase 1 Focus:** Focus is strictly on Tier 1 (Unit) and Tier 2 (Integration via Docker/OrbStack). Tier 3 (E2E) is deferred to later multi-service phases.  
> **Applies to:** All Stratum Repositories (`services/*`, `gateway`, `web`, `meta`)

---

## 🏛️ Executive Overview

In **Stratum**, 100% of software code and infrastructure is generated by AI agents governed by Human-in-the-Loop review. Because code is authored autonomously, **testing is not an afterthought—it is the executable specification of the entire system.**

Stratum strictly follows **Test-Driven Development (TDD)** and organizes verification into three distinct architectural tiers:

```
                          ▲
                         / \
                        /   \
                       / E2E \       Tier 3: End-to-End Testing (Cross-Service Journeys)
                      /------- \     Target: Cloud UAT | Runner: Local Workstation (PC)
                     /          \
                    / Integration\   Tier 2: Component & Seam Testing (Real DB / Redis Containers)
                   /--------------\  Target: Isolated Repo Sandbox (Testcontainers)
                  /                \
                 /    Unit Tests    \ Tier 1: Pure Logic in Memory (100% Mocked)
                /--------------------\ Target: Local Workspace / CI (Sub-second)
```

## 📚 Formal Testing Foundations & Taxonomy (ISO/IEC/IEEE 29119 & ISTQB)

To ensure universal technical precision across all human reviews and autonomous AI engineering prompts, Stratum pins its verification taxonomy to canonical, version-dated international standards:

### 1. Canonical Standards & Publication Lifecycles
* **ISO/IEC/IEEE 29119 (Software and Systems Engineering — Software Testing):**
  * *ISO/IEC/IEEE 29119-1:2022* (Concepts & Definitions — 2nd Edition, Published **January 2022**; original standard published September 2013).
  * *ISO/IEC/IEEE 29119-2:2021* (Test Processes — 2nd Edition, Published **November 2021**).
  * *ISO/IEC/IEEE 29119-3:2021* (Test Documentation & Test Cases — 2nd Edition, Published **October 2021**).
  * *ISO/IEC/IEEE 29119-4:2021* (Test Techniques — 2nd Edition, Published **October 2021**).
* **ISTQB Standard Glossary of Terms Used in Software Testing:**
  * Version **4.0** (Published **May 2023** by the International Software Testing Qualifications Board; aligned with ISTQB Certified Tester Foundation Level v4.0).
* **BDD (Behavior-Driven Development / Specification by Example):**
  * Formalized by Dan North (**2006**) and canonical industry reference *Specification by Example: How Successful Teams Deliver the Right Software* by Gojko Adzic (**June 2011**).

### 2. Standardized Testing Taxonomy

| Concept | Formal ISTQB / ISO 29119 Definition | Meaning in Stratum (Human & AI) | Concrete Examples |
| :--- | :--- | :--- | :--- |
| **Test Assertion** | The atomic check of a single observable state or value. | A single line verification (`assert a == b`). | Checking that `status_code == 200` or `amount == Decimal("75000.00")`. |
| **Test Case** | A set of preconditions, inputs, actions, expected results, and postconditions developed for a particular test condition (strictly agnostic to manual or automated execution). | A specific situation or input variation being evaluated. | • **Case 1:** Inbox is empty.<br>• **Case 2:** Inbox has 1 VIB email.<br>• **Case 3:** Inbox has multiple VIB emails.<br>• **Case 4:** Non-bank email noise.<br>• **Unhappy Case:** IMAP server unreachable. |
| **Test Scenario** | An end-to-end operational story or business journey spanning multiple steps and boundaries. | Complete user workflow from external trigger to final stakeholder outcome. | Human has bank email in inbox → triggers batch → movement saved in DB → real Viber alert received on phone. |
| **Test Fixture / Data** | Artifacts, data states, and external resources required to execute one or more test cases. | The actual sample emails, database seed rows, or configuration files fed into the test. | • Raw `.eml` files from mailbox<br>• Docker Testcontainers DB seed<br>• Mock server responses |
| **Test Suite** | A collection of test cases or test scenarios grouped for a specific execution objective. | The package of tests run at a gate or lifecycle tier. | • Tier 1 Unit Suite<br>• Tier 2 Integration Suite<br>• Tier 3 UAT Verification Suite |

## 🔬 Tier 1: Unit Testing (In-Memory Isolation)

### 1.1 Definition & Purpose
Unit tests verify the smallest testable units of code (functions, pure domain entities, state transitions, mathematical calculations, and parsing logic) in complete isolation.

### 1.2 Key Rules
* **Zero Network, Zero Disk:** Unit tests must never make real network calls, connect to databases, or access the host filesystem.
* **100% Deterministic:** Unit tests must produce identical results regardless of environment, timezone, or machine state.
* **Blistering Speed:** Thousands of unit tests must execute in seconds to enable rapid inner-loop AI development.

### 1.3 Examples in Stratum
* Verifying that an email address parser in `gateway` correctly parses RFC 5322 headers and flags invalid domains.
* Validating that a currency calculation utility in `services/cashflow` rounds fractions according to business accounting rules.
* Checking that state machine transitions in `services/cashflow` correctly transition from `PENDING_REVIEW` to `SETTLED`.

## 🔌 Tier 2: Integration Testing (Seams & Side-Effects)

### 2.1 Definition & Scope
Integration testing in Stratum verifies the seams, communications, and stateful side-effects between application code and real external subsystems (databases, caches, message brokers, and downstream service contracts). Rather than merely asserting HTTP response codes, integration tests validate that real data transitions and side-effects occur reliably.

```
                       ┌──────────────────────────────────────────────────┐
                       │          INTEGRATION TEST SCOPE                  │
                       │                                                  │
    [ HTTP / gRPC Call ]──► [ Service Logic ] ──► [ Real PostgreSQL DB ]  │  (Asserts DB rows, constraints, rollbacks)
                       │          │                                       │
                       │          ├────────────► [ Real Redis Cache ]     │  (Asserts cache hits, invalidation & TTL)
                       │          │                                       │
                       │          └────────────► [ Real Kafka / Queue ]   │  (Asserts event emission & consumer ack)
                       └──────────────────────────────────────────────────┘
```

### 2.2 What Integration Tests Assert (Beyond API Payload)
1. **Database Persistence & Constraints:**
   - Did the record actually write to a real PostgreSQL database?
   - Are unique keys, foreign keys, and check constraints enforced?
   - Do database migrations run cleanly?
   - Do transactional rollbacks successfully revert state when an unhandled error occurs?
2. **Event & Message Bus Seams:**
   - When an order is placed, was an `OrderCreatedEvent` published to the message broker?
   - Are messages serialized correctly according to protobuf/Avro/JSON schemas?
   - Does a consumer correctly acknowledge (`ack`) or dead-letter (`nack`) malformed messages?
3. **Cache & State Stores:**
   - Does a cache hit return cached data without querying the database?
   - Does a mutation invalidate the appropriate cache keys in Redis?
4. **Resilience & Fault Tolerance:**
   - How does the service behave when the database times out or returns a connection error? Does it retry gracefully or return a sanitized error message?

### 2.3 Independent Repository Isolation via Testcontainers
In Stratum's multi-repository architecture, each repository must be developed and tested **completely independently**:
* Microservice repositories (`services/cashflow`) must **never** depend on running sibling services (`services/auth`) during integration tests.
* Instead, integration tests use **Testcontainers** (ephemeral Docker containers managed programmatically):
  - When tests start, Testcontainers spins up a real, clean PostgreSQL or Redis container in OrbStack/Docker.
  - Sibling microservices and external third-party APIs (e.g. Zalo Bot API, Payment Gateways) are simulated using strict **HTTP WireMocks** or **OpenAPI Contract Mocks**.
* **Repository-Scoped Scenarios & Fixtures:** Because Tier 1 (Unit) and Tier 2 (Integration) tests run against a single isolated repository, both the test scenarios (`scenario.md` reviewed at `GATE-02`) and test fixtures (`fixtures/` containing sample emails, mock payloads, or seed data) are housed **directly in that specific repository** (e.g., `<repo>/changes/CR-YYaXXX-<short-title>/`). They do not live in the global `meta` archive.
* **Benefit:** 100% of integration tests pass in complete isolation on your local machine before staging is ever touched.

## 🌐 Tier 3: End-to-End (E2E) Testing (Cross-Service Journeys)

### 3.1 Definition & Purpose
End-to-End (E2E) testing verifies that the **entire interconnected ecosystem** functions correctly from the outside in. It simulates actual human user journeys across multiple microservices, networks, databases, and communication channels.

---

### 3.2 The Early-Phase Dilemma: Why E2E is Complicated & When to Defer It

#### The Concerns with Early E2E Automation:
1. **High Setup Complexity:** Requires spinning up and coordinating 5–10 separate microservices, network ingresses, and shared state stores.
2. **Schema & Contract Churn:** In early development, APIs and data models change daily. Full E2E automation scripts break constantly, requiring heavy maintenance.
3. **Test Data Pollution:** Automated E2E tests create and mutate data across multiple databases, creating collisions if human testers are in the same environment.
4. **False-Positive Flakiness:** Network blips, asynchronous delays, and browser rendering timeouts can cause tests to fail even when code is correct.

#### The Pragmatic "Bridge Strategy" (How to stay 90% safe early on):
During early phases, you can safely **defer complex E2E journey automation** by relying on three lightweight bridges:
1. **Rigorous Integration Tests (Tier 2):** Testcontainers + OpenAPI schema enforcement catches **85–90%** of bugs inside the repo sandbox.
2. **Lightweight Staging Smoke Checks:** Run simple automated health and ping checks (`/healthz`, `/ready`, basic HTTP ping) to ensure services are wired up without writing complex stateful journey tests.
3. **Human UAT Walkthrough (`GATE-03`):** The human stakeholder spends 2–3 minutes exploring the feature live in the UAT environment before production rollout.
4. **Canary Rollout & AIOps Rollback:** If a cross-service bug slips through, canary progressive delivery (10% traffic shift) and AIOps error monitoring automatically abort the rollout.

#### When SHOULD You Introduce Full Automated E2E?
Bring in full automated E2E testing when:
* You have **more than 3–4 interdependent microservices**.
* Manual testing at `GATE-03` starts taking **more than 10–15 minutes** per release.
* Core API contracts and data models have stabilized.

---

### 3.3 Sequence: Why Automated E2E Must Be BEFORE UAT

```
[Deploy to UAT] ──► [ Automated E2E Runs (Pre-flight) ]
                            │
               ┌────────────┴────────────┐
           [Passed]                  [Failed]
               │                         │
               ▼                         ▼
   [GATE-03: Human UAT Sign-off]    [Alert AI Dev Agent]
   (Human tests with confidence)    (Human is NEVER bothered)
```

**Automated E2E must ALWAYS precede human User Acceptance Testing:**
1. **Respects Human Attention:** Human testing is expensive; automated tests cost pennies. A human should never spend 20 minutes testing a feature only to discover a broken database trigger that a script could have caught in 10 seconds.
2. **Automated Quality Bouncer:** E2E acts as the gatekeeper that qualifies a release candidate. If basic cross-service wiring fails, the build is blocked and returned to the AI agent immediately—the human is never pinged.
3. **High-Confidence UAT:** When you receive the UAT review notification, you know all baseline technical journeys have passed. You are evaluating business nuances and user experience, not debugging 500 errors.

### 3.4 Execution Topology: Local Workstation (Runner) vs. Cloud (UAT Target)

A major architectural question is: **Where should UAT live, and where should the E2E test runner execute?**

The optimal hybrid setup for Stratum is:
* **The UAT Environment lives on the CLOUD.**
* **The Automated E2E Runner executes on your LOCAL WORKSTATION / HOST MACHINE (PC / Mac Studio).**

```
┌─────────────────────────────────────────┐             ┌─────────────────────────────────────────┐
│  LOCAL WORKSTATION / HOST RUNNER (PC)   │             │         CLOUD INFRASTRUCTURE            │
├─────────────────────────────────────────┤             ├─────────────────────────────────────────┤
│                                         │             │                                         │
│ • Heavy E2E Test Runner                 │             │ • UAT Application Containers            │
│ • Headless Browsers (Playwright)        │             │ • UAT Databases & Message Queues        │
│ • Synthetic Load Generators             │             │ • Live Webhooks (Zalo / Viber / Email)  │
│ • $0 Cloud Compute Billed               │             │ • Stable Public URL: `https://uat...`   │
│                                         │             │                                         │
│        [ Automated Test Runner ] ───────┼─────────────┼───────────────► [ Cloud UAT Target ]    │
│     (Sends HTTP/browser traffic         │  Internet   │            (Receives & processes calls) │
│        over public internet)            │   (HTTPS)   │                                         │
└─────────────────────────────────────────┘             └─────────────────────────────────────────┘
```

#### Why this hybrid topology is superior:
1. **True 24/7 Availability for Real Users & Webhooks (Cloud UAT):**
   - The UAT application is accessible from anywhere in the world at `https://uat.stratum.yourdomain.com`.
   - Zalo and Viber cloud servers send webhooks directly to a stable cloud domain with zero local tunneling required.
   - Stakeholders can test from their phones on 4G without caring whether your local workstation is on or off.
2. **Zero Cloud CI Bills (Local Workstation Runner):**
   - Running 10–20 parallel headless Chrome/WebKit browser instances is very CPU- and memory-intensive. Running that on cloud CI (like GitHub Actions) gets expensive quickly.
   - Your local workstation (e.g. Mac Studio M-series CPU with unified memory) executes hundreds of browser journeys simultaneously in seconds for **$0**.
3. **Real "Outside-In" Black-Box Testing:**
   - Because the test runner executes on your workstation and hits the cloud UAT over the public internet, it tests the **exact real-world user experience**: real DNS resolution, real SSL handshakes, CDN caching, and mobile network latency.

### 3.5 Tier 3 (UAT) Universal Production-Parity Standards

To eliminate artificial sandbox blind spots, UAT must mirror real operational conditions:

1. **Maximum Real Components (Live Boundary Standard):**
   * UAT must execute against live external boundaries (e.g., real mailbox polling via IMAP, real on-device host LLM GPU inference, real containerized database, real messaging webhooks like Viber).
   * **FORBIDDEN:** Creating artificial "simulation" or "cheat" endpoints inside production containers solely for testing.
2. **Maximum Real Data (Test Data Acceptable):**
   * UAT prioritizes real historical data from active production channels (e.g. real emails from the stakeholder mailbox covering diverse layouts, formatting quirks, and real-world edge cases).
   * Curated test data (sanitized fixtures or synthetic stress-test payloads) is acceptable when real data is unavailable or to safely evaluate critical failure/unhappy paths.

### 3.6 Shift-Left UAT Suite Review: GATE-02 vs. GATE-03

A critical architectural invariant is that **the entire UAT Test Suite must be reviewed and approved at `GATE-02`, not `GATE-03`**:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 🛡️ GATE-02: Contract & Test Scenario Gate (BEFORE Code Synthesis)     │
├────────────────────────────────────────────────────────────────────────┤
│ • Human Stakeholder reviews:                                          │
│   1. Technical Specification & DB Schemas.                            │
│   2. Tier 1 & Tier 2 Test Cases.                                      │
│   3. Complete Tier 3 UAT Test Suite (Happy, Edge, and Unhappy Cases).  │
│ • Impact: AI Dev Agent receives explicit requirements in STEP-05 for   │
│   graceful error handling, retries, and structured logging BEFORE      │
│   synthesizing code.                                                   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (Code synthesized in STEP-05)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 🛡️ GATE-03: User Acceptance Gate (Execution & Physical Verification)  │
├────────────────────────────────────────────────────────────────────────┤
│ • AI Agent executes the pre-approved UAT Suite automatically.         │
│ • Human Stakeholder:                                                  │
│   1. Reviews the automated execution scorecard.                       │
│   2. Performs physical human-only verifications (e.g., verifying the   │
│      Viber alert arrived on their physical mobile phone screen).       │
│   3. Signs off on production promotion.                               │
└────────────────────────────────────────────────────────────────────────┘
```

#### Why Shift-Left Suite Review is Mandatory:
* If unhappy paths (e.g., external server unreachable, network timeout, malformed payload, empty inbox) are only introduced at `GATE-03`, implementation code will fail because the AI agent was never instructed to build the requisite error handlers and fallbacks.
* Specifying the complete suite at `GATE-02` guarantees that code synthesized in `STEP-05` is resilient by design.

### 3.7 UAT-to-Integration Fixture Feedback Loop (Traffic Shadowing / Replay Fixtures)

Live acceptance testing must continuously reinforce automated regression defenses:

```
[Phase 3: Live UAT] 
         │ (1. Harvest Raw Payload)
         ▼
[Temp Capture Log: scratch/harvested_*.raw]
         │ (2. Automated Sanitization: Redact Secrets/Tokens, Keep Structure)
         ▼
[Sanitized Fixture: <repo>/tests/fixtures/real_<source>_<timestamp>.<ext>]
         │ (3. Promotion in STEP-07)
         ▼
[Tier 2 Integration Test parameterized with new fixture]
         │ (4. Permanent Regression Defense)
[Every future git commit runs pytest against this real fixture automatically]
```

1. **Harvesting:** During live UAT, raw incoming payloads (emails, webhooks, API requests) are captured into local run artifacts.
2. **Sanitization:** Credentials, API keys, and private tokens are redacted or replaced with standard dummy values, while keeping exact character sequences, body formatting, timestamps, and numeric fields verbatim.
3. **Promotion (`STEP-07`):** Upon `GATE-03` sign-off, sanitized files are promoted to the target repository's regression fixture directory (`<repo>/tests/fixtures/`).
4. **Regression Binding:** The repository's Tier 2 integration test suite is parameterized with the new fixture. Future code synthesis can never regress against real-world data formats.

## 🎯 Summary Takeaways

1. **Unit Tests (Tier 1):** Fast, in-memory, zero-dependency. Catch logic flaws instantly. Authored in `STEP-04` (Red), satisfied in `STEP-05` (Green).
2. **Integration Tests (Tier 2):** Essential. Test real database constraints, transactions, and event streams via Testcontainers inside isolated repositories. Catch 85–90% of bugs before staging. Authored in `STEP-04` (Red), satisfied in `STEP-05` (Green).
3. **End-to-End Tests (Tier 3):** Validate full user journeys across services. Defer complex multi-repo E2E automation early on; rely on integration tests + lightweight smoke pings until APIs stabilize. Executed in `STEP-06` before `GATE-03`.
4. **Pre-Flight Runs Before UAT:** Always pre-flight test automatically in `STEP-06` before asking a human to inspect UAT at `GATE-03`.
5. **Local Portability:** Run Tier 1 and Tier 2 tests locally with zero cloud dependencies; run live UAT containers locally on OrbStack or deploy seamlessly to cloud.
